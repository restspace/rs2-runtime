# 4.8 Schema annotations: the authoring contract for editing clients

A dataset's `.schema.json` does more than validate writes (4.5) — it is the
**client contract** for the records it describes. A generic editing client (a
CMS-style UI, an admin panel, an AI agent building a form) derives everything
from it: field types and labels from the properties, validation from the
constraints, and — with the small vocabulary below — *how to edit* each field
and *how to preview* the result.

These annotations are plain `x-…` keys in the JSON Schema. The runtime passes
them through untouched (validators ignore unknown keywords), so they cost
nothing at write time; they exist purely for clients, which **feature-detect
them on the schema** — never keyed off a service name, in the spirit of 3.4.
Any client that understands the vocabulary gets the same editing surface from
the same schema, with no client-specific config anywhere.

## The vocabulary

| Annotation | Where | Meaning |
| --- | --- | --- |
| `format: "markdown"` | field | Standard JSON Schema `format`, recognized as a shortcut: edit this string field with a markdown editor |
| `x-editor` | field | Force a specific field editor by key (e.g. `"markdown"`, `"image"`); wins over any inferred editor |
| `x-media-mount` | field or schema root | The file mount an image field browses and uploads into (e.g. `"/media"`). Field-level implies the image picker for that field; at the schema root it is the form-level default |
| `x-preview` | schema root | How a record maps to its rendered page, for a live preview beside the form (below) |

## Example

```json
{ "type": "object",
  "x-media-mount": "/media",
  "x-preview": "/site/{slug}",
  "required": ["title", "slug"],
  "properties": {
    "title": { "type": "string" },
    "slug":  { "type": "string" },
    "body":  { "type": "string", "format": "markdown" },
    "hero":  { "type": "string", "x-editor": "image" }
  } }
```

An editing client renders `title` and `slug` as plain inputs, `body` as a
markdown editor, and `hero` as an image picker browsing `/media`; the preview
pane renders `GET /site/{slug}` with the record's `slug` substituted.

## `x-preview`: record → rendered page

Two forms:

- **A path template string** — `"/site/{slug}"`. `{field}` tokens substitute
  top-level field values from the record; the client `GET`s the resulting
  path. Simple, but reflects the **last-saved** state (the rendering pipeline
  reads the store).
- **An object** — `{ "path": "/render/page", "method": "POST", "body": "self" }`.
  The client `POST`s the **live record** (`body: "self"`) to the path, so a
  template mount (6.6) renders the in-progress edits — a genuine unsaved-changes
  preview. `method` defaults to `GET`.

## Relation to the other schema families

The schema is also where **field-level access** lives (`x-rs-read` /
`x-rs-write`, 4.5) — enforced by the runtime, unlike the authoring vocabulary
above, which is advisory to clients. Both follow the same principle: the
record's shape, its rules, and its editing experience travel together in one
document the runtime serves and points to from every read (the
schema-carrying content type, 4.5), so there is nothing to drift.

For mount-level (rather than field-level) client hints — patterns, facets,
`specSubtree`, `authoring` — see the discovery surface (9.1). To scope which
mounts an editing client sees at all, use `x-expose` on the mount and query
the catalogue with `?surface=<name>` (also 9.1).
