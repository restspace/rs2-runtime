# 4.6 Listings, pagination, and the `?confirm=` delete guard

These behaviors are part of the store contract (3.3), so they're identical on
`file`, `data`, and any other store. This section is the practical reference for
the two operations clients get wrong most often: listing/paging containers and
deleting non-empty ones.

## Listings

A trailing-slash `GET` lists a container as `application/vnd.rs2.dir+json`:

```json
{
  "path": "/people/",
  "entries": [
    { "name": "ada", "dir": false },
    { "name": "archive", "dir": true }
  ],
  "total": 42
}
```

- `entries` — children at this level; `dir: true` marks a sub-container you can
  list in turn.
- `total` — the full count, also returned as the `X-Total-Count` header.
- Listings work at **every** level, including the mount root.

To walk a whole tree, recurse into entries where `dir` is `true` (the generic
client loop, 3.3).

## Pagination

Large containers page with two query params:

| Param | Meaning | Default / cap |
| --- | --- | --- |
| `$take` | Max entries to return | default 1000, max 10000 |
| `$skip` | Entries to skip | default 0 |

```
GET /data/events/?$take=100&$skip=200
```

`X-Total-Count` always reflects the full size, so a client can compute how many
pages remain regardless of the page it asked for. (The `$`-prefix marks these as
**control** params, distinct from query parameters a `query` mount would
consume — see Part 6.)

## Projected listings on `data` (`$select` / `$sort`)

A plain listing gives you names; rendering a record table from it costs one GET
per row. `data` mounts (the `list-projection` facet) close that gap: a dataset
listing can **project fields into the entries** and sort by them, so a
CMS-style admin UI fills a table in one round trip.

```
GET /data/articles/?$select=title,meta.date&$sort=-meta.date&$take=25
```

- `$select` — comma-separated dot-paths into each record. Every entry gains a
  `fields` object with the projected values; nested paths keep their shape
  (`meta.date` → `"fields": {"meta": {"date": …}}`), absent paths are simply
  omitted. The `.schema.json` fixed entry is excluded — a projected listing is
  record rows only.
- `$sort` — comma-separated sort keys, `-` prefix for descending
  (`-meta.date,title`). Only valid **with** `$select`; `$sort` alone is a 400
  (no silent parameter-dropping).
- `$take`/`$skip` and `X-Total-Count` work as above: the page is cut **after**
  the sort, and `total` stays the full dataset count.

```json
{
  "path": "/articles/",
  "entries": [
    { "name": "hello-rs2", "dir": false, "contentType": "application/json",
      "fields": { "title": "Hello RS2", "meta": { "date": "2026-07-01" } } }
  ],
  "total": 42
}
```

Field-level authz (4.4's `x-rs-read` rules) redacts projected fields exactly as
a record GET would — a listing never leaks what a single read hides.

**Sort semantics are pinned** so every backend gives the same answer: strings
compare by binary UTF-8 code points (case-sensitive, no locale — `"Zebra"` <
`"apple"`), and across types missing < null < false < true < numbers < strings
< arrays < objects, with the record key as the final tiebreak. This is
contractual for homogeneous scalar fields; for human alphabetization, compute a
materialized sort-key field (e.g. a lowercased title) at write time and sort on
that.

**Cost.** The services doc entry for a data mount carries `listProjection:
"native" | "fallback"`. Native means the adapter pushes projection and sort
down to its engine (e.g. `builtin:mem`, or a guest adapter that advertises it);
fallback means the host walks keys — the whole dataset under a `$sort`, only
the requested page without one.

## Metadata sort on file listings (`$sort=@…`)

File-pattern listings (the `meta-sort` facet: `file` mounts and every spec
store's authoring subtree) accept `$sort` over what the listing already knows
about each entry — no content is read:

```
GET /assets/img/?$sort=-@lastModified&$take=25
```

- Keys are `@`-prefixed: `@name`, `@size`, `@lastModified`, `@contentType`,
  `@dir`; `-` for descending, comma-separated for multi-key. The `@` namespace
  keeps metadata distinct from content fields (which stay `data`-only for now).
- Same pinned comparison semantics as above; entries missing a value (a
  directory's `@contentType`, an adapter without timestamps) sort first
  ascending; entry name breaks ties. `lastModified` is RFC 3339, which sorts
  chronologically under the binary string compare.
- `$take`/`$skip` cut the page **after** the sort; `total` stays the full
  directory count. Unknown or unprefixed keys are a 400, never ignored.

`-@lastModified` is the one to remember: "most recently modified first" over
any folder — the natural default view for an editing UI.

## Deleting a child

`DELETE <child>` returns `204`. Straightforward.

## Deleting a container — the `?confirm=` guard

Deleting a container is guarded so you can't wipe a populated tree by accident:

```
DELETE /data/events/
→ 409 Conflict          (non-empty container)

DELETE /data/events/?confirm=events
→ 204 No Content
```

- An **empty**, unguarded container deletes with `204`.
- A **non-empty** container returns `409`; you must retry with
  `?confirm=<container name>` to actually delete it.
- The `data` service goes further: **dataset deletes always require the confirm
  token**, empty or not.

A robust client treats `409` on a container delete as "ask for confirmation, then
retry with `?confirm=`" — exactly the generic loop step from 3.3.
