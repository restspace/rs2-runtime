# 5.6 API keys

A login token (5.3) lasts an hour and is renewed by a client that can run the
login flow. Some clients can't: an MCP client configured once with a header, a
cron script, CI. For those, mount the **`apikeys`** service. A key is a
long-lived, revocable bearer credential that acts as the user who made it,
with the roles they chose to give it.

Keys are off unless the mount exists. Without it, a key is just an unrecognised
bearer token and is refused with `401`.

## Setup

```json
{ "path": "/keys", "service": "apikeys",
  "config": {
    "access": { "read": "authenticated", "invoke": "authenticated",
                "delete": "authenticated" },
    "maxDays": 90,
    "adminRole": "A"
  } }
```

| Config | Default | Meaning |
| --- | --- | --- |
| `maxDays` | `90` | The longest lifetime a key may have. Every key expires within it. |
| `adminRole` | none | A role that may list and revoke every key, not only its own. |
| `dataset` | `apikeys` | Where key records are stored. |

The tenant needs `auth.jwtSecret` (5.1): it seals the key records (see below).
Rotating it invalidates every key, just as it invalidates every token.

## Using it

| Request | Does |
| --- | --- |
| `POST /keys` `{name, roles?, expiresInDays?}` | `201` with `{id, key, name, owner, roles, created, expires}`. **`key` is shown this once**; store it now. |
| `GET /keys` | Your keys (every key, for `adminRole`), without secrets |
| `DELETE /keys/<id>` | Revoke: `204`. Someone else's key is a `404`, as if it didn't exist. |

- `roles` defaults to all of yours and may not include a role you don't hold
  (`403`). Give a key the least it needs.
- `expiresInDays` is 1 to `maxDays` (default `maxDays`).
- Creating a key needs a login. A request authenticated by a key can list and
  revoke keys but **cannot create** them, so a leaked key can't be used to
  make more.

Send a key like a token: `Authorization: Bearer rs2k_…`. Keys are accepted
only in that header, never as a cookie. The request then runs as the key's
owner with the key's roles: `GET /auth/user` shows the owner's `id`, the key's
`roles`, `kind: "key"`, the owner's extra claims (`jwtUserProps`) as they were
when the key was made, and `keyId`. An unknown, revoked, expired or malformed
key is a `401`, never anonymous.

For example, connecting an MCP client to an `mcp` mount:

```bash
claude mcp add --transport http rs2 https://api.example.com/mcp \
  --header "Authorization: Bearer rs2k_…"
```

## What a key keeps, and what it doesn't

- **The roles are fixed when the key is made.** Taking a role away from a user
  doesn't shrink their existing keys. Revoke and reissue them; `maxDays` bounds
  how long a forgotten one lasts.
- **The secret is never stored.** A key is `rs2k_<id>_<secret>`. The record
  under `<id>` holds the name, owner, roles, times and a *seal*: an HMAC over
  the secret and every field, keyed by `auth.jwtSecret`. Nothing in it lets
  anyone rebuild the key.
- **Records can't be forged.** The records sit in the tenant's data store, so
  a `data` mount over the same store can read and write them. A record
  rewritten that way (say, to add role `A`) or planted from scratch fails the
  seal and grants nothing. Deleting one revokes the key. Even so, keep the
  `apikeys` dataset out of any data mount's reach where you can.

## How it fits

`apikeys` and `auth` are both *authenticators*: the host offers each request
to every authenticating mount in turn, and each recognises only its own
credential (a JWT, or an `rs2k_` key). So a tenant can use either or both, and
the order of the mounts doesn't matter.
